# Phase 1 — Design Principles

**Why here:** principles are the *reasons* behind patterns. Every pattern in Phases 2–4 is derived as
"the structure that keeps this change local" (OCP), "the abstraction the policy should own" (DIP), and
so on. A candidate who can only name patterns over-applies them; a candidate who reasons from the cost
of change applies them where they pay. Each SOLID principle gets its own session with a **violation →
requirement change → refactor**, because the violation only hurts when requirements move.
**Scaffolding:** hints on request at any rung; Claude offers H0 after ~5 min of silence.
**Reading (after the sessions):** optional: *Clean Architecture* (Martin) ch 7–11 (the SOLID chapters);
*A Philosophy of Software Design* (Ousterhout) ch 4–5 (deep modules, information hiding) for 1.1.1.

## Cycle 1.1 — Cohesion, coupling and SOLID

| ID | Type | Session |
|---|---|---|
| 1.1.1 | L | **Cohesion, Coupling & the Cost of Change** — Hook: "Changing the GST rate touched 7 files in 4 modules, and a report broke that has nothing to do with tax. Why?" · Derive: the knowledge 'how tax is computed' is scattered (low cohesion) and many modules depend on its details (high coupling) → a change's blast radius = what knows the detail → gather what changes together, separate what changes for different reasons, depend on stable things · Covers: cohesion (functional … coincidental, informally: "does everything in here change for the same reason?"); coupling kinds (content, common/global, control flags, stamp, data) and why data coupling is the goal; connascence (name, type, meaning, position, algorithm, timing) as a vocabulary for *how* things are coupled; information hiding (Parnas 1972: modules hide design decisions likely to change); deep vs shallow modules (Ousterhout); measuring a design by "how many files does a plausible change touch?"; afferent/efferent coupling and stability (brief) · Build: `designs/phase-01/tax/`: a scattered tax computation refactored into one cohesive module with a narrow interface; count the files touched by 3 rate changes before and after · Adapt: state-wise cess; a tax holiday for one category; showing tax breakdown on invoices · Anchors: the tax example, Parnas' KWIC index, "shotgun surgery" code · When-NOT: chasing zero coupling (everything behind an interface) makes code harder to follow; some coupling to stable things (the standard library, value objects) is free · File: `lessons/phase-01/1.1.1-Cohesion-Coupling.md` |
| 1.1.2 | L | **Single Responsibility Principle** — Hook: "`Employee` has `calculatePay()` (finance's rules), `reportHours()` (HR's rules) and `save()` (the DBA's schema). Finance changes overtime; HR's report is now wrong" · Derive: two methods shared a helper (`regularHours()`) because the code looked the same → a change requested by one actor broke another → a responsibility is *a reason to change*, i.e. an actor/stakeholder → separate what different actors own · Covers: SRP as "one actor" (Martin's reformulation), not "one method" or "does one thing"; accidental duplication vs true duplication; symptoms (merge conflicts between teams, divergent change, classes named `…Manager`); refactors: extract class, facade over split classes, data class + separate calculators; granularity trap (a class per method); SRP at function, class and module level · Build: `designs/phase-01/srp-employee/`: the violating `Employee` with a test showing the cross-actor breakage, then the refactor (`PayCalculator`, `HourReporter`, `EmployeeRepository`, `EmployeeFacade`); Java version · Adapt: a third actor (compliance) wants an audit export; overtime rules differ for contractors · Anchors: Employee (Clean Architecture), `Report` that computes + formats + prints, `UserService` doing auth + profile + email · When-NOT: splitting a small cohesive class into five because "it does more than one thing"; SRP is about sources of change, not line counts · File: `lessons/phase-01/1.1.2-SRP.md` |
| 1.1.3 | L | **Open/Closed Principle** — Hook: "`DiscountCalculator::apply()` is a `switch` on customer type with 6 cases. Marketing adds a new offer every sprint; each release breaks an old offer" · Derive: every new variant edits (and risks) the tested function → identify the axis of variation (discount kinds) → put each variant behind an abstraction; the core depends on the abstraction → new behaviour = new code, not edited code · Covers: "open for extension, closed for modification" (Meyer's inheritance version vs Martin's polymorphic version); axes of change and why you must *predict* them (OCP is only possible along anticipated axes); mechanisms: polymorphism, strategy objects, lambdas/`std::function`, registries/plugins, configuration/data-driven rules; OCP at the module level (plugins); the cost: indirection, more types; the tension with YAGNI and the "rule of three" to decide when · Build: `designs/phase-01/ocp-discounts/`: the switch version with tests, then an OCP version where adding a discount is one new class + one registration line; show the diff for adding "festival sale" in both · Adapt: two discounts that stack with a priority; a discount that depends on the cart, not the customer (does your abstraction's signature survive?); discounts defined in a config file · Anchors: discount calculator, shape area, report exporters · When-NOT: a closed, stable set (days of the week, the 4 card suits) → a `switch` over an `enum class` is clearer and the compiler checks exhaustiveness · File: `lessons/phase-01/1.1.3-OCP.md` |
| 1.1.4 | L | **Liskov Substitution Principle** — Hook: "`Square : Rectangle` passes every Square test. Then `resizeToFit(Rectangle&)` sets width then height and asserts the area; it fails for squares. Also: `Penguin : Bird` and `bird.fly()`" · Derive: the subclass is a subtype by syntax but not by *behaviour*: it breaks what callers were promised → substitutability is about contracts → preconditions can't be strengthened, postconditions can't be weakened, invariants and history must be preserved · Covers: behavioural subtyping (Liskov & Wing); contract rules (pre/post/invariant/history constraint); exceptions as contract violations (`UnsupportedOperationException` in Java's unmodifiable collections: a documented LSP compromise and its cost); `instanceof`/`dynamic_cast` checks in callers as the smell; fixes: redesign the hierarchy (separate `Shape` types), composition, capability interfaces (`Flyer`), immutability (an immutable Square *is* a valid immutable Rectangle); contract tests: one test suite run against every implementation · Build: `designs/phase-01/lsp/`: reproduce the Rectangle/Square failure in a test; write a contract test suite for a `Storage` interface and run it against 3 implementations, one of which violates it · Adapt: a `ReadOnlyAccount : Account`; a `CachedRepository` that returns stale data (is that an LSP violation?); a subclass that adds validation (stronger precondition) · Anchors: Rectangle/Square, Bird/Penguin, Java `List.of().add()` · When-NOT: LSP doesn't forbid inheritance; it forbids *lying* subtypes. Don't flatten a correct hierarchy out of fear · File: `lessons/phase-01/1.1.4-LSP.md` |
| 1.1.5 | L | **Interface Segregation Principle** — Hook: "`IMachine { print(); scan(); fax(); staple(); }`. The cheap printer implements `fax()` by throwing; every change to `staple()` recompiles and redeploys the kiosk that only prints" · Derive: clients depend on methods they don't use → they break and rebuild for changes they don't care about, and implementers fake methods (LSP violations) → split by *client need* into role interfaces · Covers: fat interfaces and header dependencies in C++ (recompilation cascades); role interfaces designed from the client side; one class implementing several small interfaces (C++ multiple abstract bases; Java multiple `implements`); ISP vs SRP (clients vs actors); interface pollution; ISP in APIs (don't return a mutable collection when the client only iterates) · Build: `designs/phase-01/isp-printer/`: split `IMachine` into `Printer`/`Scanner`/`Fax`; a multifunction device implementing all; clients depending only on what they use; Java version · Adapt: a "copy" operation that needs print + scan; a remote device where scan is async · Anchors: printer/scanner, `Worker { work(); eat(); }` with robots, repository interfaces split into reader/writer · When-NOT: a one-method interface per method ("interface soup"); if all clients use all methods, one interface is right · File: `lessons/phase-01/1.1.5-ISP.md` |
| 1.1.6 | L | **Dependency Inversion Principle** — Hook: "`OrderService` constructs a `MySqlOrderDao` and a `RazorpayClient` inside its constructor. Now: run the tests without a database, and switch one merchant to another payment gateway" · Derive: high-level policy depends on low-level details → details can't change without touching policy, and policy can't be tested alone → the policy defines the interface it needs (the *port*) and details implement it → the source-code dependency now points *against* the flow of control · Covers: the two rules (both depend on abstractions; abstractions don't depend on details); **interface ownership** (the client/policy owns the interface, so it lives with the policy); DIP vs DI vs IoC (principle vs technique vs framework property); constructor injection as the default; the composition root (the one place that wires concretes: `main`); stable abstractions; DIP at package level (dependency direction between modules) · Build: `designs/phase-01/dip-orders/`: the tangled `OrderService`, then the inverted version with `OrderRepository` and `PaymentGateway` owned by the domain, in-memory fakes for tests, wiring in `main`; Java version · Adapt: a second gateway chosen per merchant at runtime; a repository that needs a transaction (does the interface leak SQL?) · Anchors: order service, notification service with channel senders, reporting with data sources · When-NOT: inverting a dependency on something stable and pure (`std::vector`, a `Money` value type, a math function) adds nothing · File: `lessons/phase-01/1.1.6-DIP.md` |
| 1.1.7 | CR | **Critique: SOLID violations and SOLID over-application**: Claude presents a confident "SOLID-compliant" invoicing module with planted flaws (private): an SRP violation that looks cohesive (formatting + tax + persistence), an OCP-violating `switch` hidden in a factory used in 3 places, an LSP-violating subclass that throws, a fat interface forcing stub methods, a service that `new`s its repository; *and* over-application: an interface with exactly one implementation and no test seam, a `StrategyFactoryProvider`. ## Cycle 1.2 — Beyond SOLID

| ID | Type | Session |
|---|---|---|
| 1.2.1 | L | **DRY, KISS, YAGNI & the Wrong Abstraction** — Hook: "Two functions, `validateSignup()` and `validateCheckout()`, share 80% of their lines. A colleague merged them into `validate(bool isSignup, bool skipPhone, bool legacyMode)`. Six months later nobody can change it" · Derive: DRY is about *knowledge*, not text → the two functions were coincidentally similar and change for different reasons → merging them coupled two actors → duplication is cheaper than the wrong abstraction (Metz); wait for the third occurrence · Covers: DRY (Hunt & Thomas: every piece of knowledge has one authoritative representation); accidental vs essential duplication; the rule of three; the wrong abstraction and how to back out of it (re-inline, then re-extract); KISS (the simplest thing that meets *today's* requirements); YAGNI (don't build for speculative requirements) vs designing seams for *likely* ones; how these interact with OCP; "boolean parameter" as an abstraction smell · Build: `designs/phase-01/dry/`: back out a wrong abstraction (inline the flag-driven function, then extract only the truly shared knowledge); tests keep both flows green · Adapt: a third flow arrives that really is the same as one of them; a requirement change hits only checkout · Anchors: validation functions, report formatters, config parsing · When-NOT: the principles themselves are over-applied: DRY-ing test code often hurts readability; YAGNI doesn't excuse skipping error handling or tests · File: `lessons/phase-01/1.2.1-DRY-KISS-YAGNI.md` |
| 1.2.2 | L | **Law of Demeter & Tell, Don't Ask** — Hook: "`order.getCustomer().getWallet().getBalance() >= total` appears in checkout, refunds and the loyalty job. Wallets move from `Customer` to a separate account service" · Derive: callers navigate a chain of internals → every link is a dependency → they break when the structure changes → ask the object that owns the data to do the work (`customer.canPay(total)`) · Covers: LoD rules (talk to self, parameters, objects you create, direct components); train wrecks vs fluent interfaces/builders (not violations: same object); Tell-Don't-Ask and feature envy; getters as a design leak; the trade-off: wrapper methods on the intermediate object (middle-man smell if overdone); LoD and testability (fewer mocks of mocks) · Build: `designs/phase-01/demeter/`: remove 3 train wrecks by moving behaviour to its data; tests before/after · Adapt: the wallet can be one of several funding sources; an admin screen legitimately needs the whole structure (DTO/read model) · Anchors: the paperboy and the wallet (Bock), order/customer chains, UI code reaching into models · When-NOT: data-transfer objects and read models are *meant* to be navigated; don't add forwarding methods for every field · File: `lessons/phase-01/1.2.2-Law-Of-Demeter.md` |
| 1.2.3 | C | **Composition over Inheritance (deep)** — Hook: "`InstrumentedHashSet extends HashSet` overrides `add` and `addAll` to count insertions. `addAll` of 3 elements reports 6" · Derive: the subclass depended on the parent's *implementation* (`addAll` calls `add`) → the fragile base class problem → wrap instead of extend (forwarding + delegation), so only the public contract is relied on · Covers: fragile base class (Effective Java item 18, the `InstrumentedHashSet` case) reproduced in C++ and Java; inheritance breaks encapsulation of the parent; forwarding classes and delegation; decorators preview; mixins and **policy-based design** with templates (C++); interfaces + default methods (Java) as partial alternatives; when inheritance is right: a genuine subtype honouring LSP, designing *for* inheritance (documented self-use, `final` otherwise, template methods with protected hooks); the comparison table (coupling, runtime flexibility, boilerplate, performance, discoverability) · Build: `designs/phase-01/instrumented-set/`: reproduce the double count with a test in C++ and Java; fix via composition; then a policy-based `Logger<Formatter, Sink>` vs a runtime-composed one, compared · Adapt: count removals too; the underlying set becomes a concurrent one; decide the composition at runtime from config · Anchors: InstrumentedHashSet, `Stack extends Vector`, game entities (component systems) · When-NOT: a small, stable, true is-a hierarchy (AST nodes, UI widgets in a framework designed for subclassing); forwarding boilerplate for 40 methods when you only need a subtype · File: `lessons/phase-01/1.2.3-Composition-Over-Inheritance.md` |
| 1.2.4 | L | **Design by Contract & Defensive Programming** — Hook: "`withdraw(amount)` is called with a negative amount from one caller and with an amount above the balance from another. Should it assert, throw, return false, or clamp?" · Derive: the answer depends on *whose bug it is*: caller's programming error (violated precondition) vs an expected domain outcome → contracts make the split explicit → preconditions checked at boundaries, invariants asserted, postconditions tested · Covers: preconditions, postconditions, invariants (Meyer, Eiffel); assertions (debug-time programmer errors) vs exceptions (runtime conditions the caller must handle) vs return values (expected outcomes); fail fast; where to validate (trust boundaries: user input, external systems) vs where to assert (internal calls); contracts in C++ (`assert`, `gsl::Expects`, the C++26 contracts direction) and Java (`Objects.requireNonNull`, `IllegalArgumentException` vs `IllegalStateException`, `assert` with `-ea`); contracts and LSP · Build: `designs/phase-01/contracts/`: `Account` and `Inventory` with explicit pre/post/invariants, a `checkInvariant()` called in debug builds, tests for each contract · Adapt: an API exposed to external clients (validation moves where?); performance-critical inner loop (keep assertions?) · Anchors: account withdraw, stack pop on empty, date parsing · When-NOT: defensive checks duplicated at every layer; asserting on user input (it's not a programmer error) · File: `lessons/phase-01/1.2.4-Design-By-Contract.md` |
| 1.2.5 | L | **Immutability** — Hook: "A `Price` object is shared by the cart, the order and the invoice. A promotion mutates it for the cart; the invoice of an already-placed order changes" · Derive: shared mutable state means any holder can change what others see → make the object impossible to change after construction → share freely, and 'change' by creating a new value · Covers: immutable objects (all fields set in the constructor, no setters, no leaked mutable internals); defensive copies; "withers" (`withQuantity(3)` returning a new object); immutability and thread safety (safe publication for free); persistent/structural sharing (idea); immutable collections (Java `List.copyOf`, Guava; C++ `const` + value types); builders for complex immutables (preview of 2.1.5); when mutation is fine (local, owned, performance-critical); C++ `const` members (and why they disable assignment) vs `const` access; Java `final` fields, records, the final-field semantics of the JMM (preview of 6.2.2) · Build: `designs/phase-01/immutable-order/`: immutable `OrderLine`/`Price`, a cart that produces an immutable `OrderSnapshot`; tests prove a later cart change can't alter the snapshot · Adapt: a price correction after order placement (new version, not mutation); a large catalogue where copying is too expensive (structural sharing) · Anchors: Money, order snapshots, config objects · When-NOT: entities with identity and a lifecycle (an `Order` moves through states) are naturally mutable; forcing immutability there creates copies that fight the domain · File: `lessons/phase-01/1.2.5-Immutability.md` |
| 1.2.6 | L | **Dependency Injection & Inversion of Control** — Hook: "`NotificationService` calls `SmsGateway::instance()` and `Clock::now()` directly. Write a test that the 'quiet hours' rule suppresses an SMS at 23:30" · Derive: hidden dependencies (singletons, statics, `new` inside) can't be replaced → pass them in → the object no longer controls its collaborators (inversion of control) → wiring moves to a composition root · Covers: constructor injection (default; makes dependencies explicit and required), setter/property injection (optional dependencies), interface/method injection; the composition root; service locator as an anti-pattern (hidden dependencies again); injecting time and randomness (`Clock`, `RandomSource`) for determinism; C++ manual DI (references vs `unique_ptr` vs `shared_ptr` for injected collaborators and who owns them), templates as compile-time injection; Java DI frameworks (Spring `@Autowired` constructor injection, Guice), why many Indian product teams use Spring Boot, and why machine-coding rounds should use **manual DI** · Build: `designs/phase-01/di-notify/`: refactor to constructor injection with `Clock` and `SmsSender` interfaces; a `FakeClock` test for quiet hours; `main` as the composition root · Adapt: per-tenant SMS provider chosen at runtime; an optional analytics dependency · Anchors: notification quiet hours, rate limiter with a clock, report scheduler · When-NOT: injecting value objects or pure utilities; 12-parameter constructors (a sign the class does too much, not that you need a container) · File: `lessons/phase-01/1.2.6-Dependency-Injection-IoC.md` |
| 1.2.7 | L | **Programming to Interfaces, Layering & Ports/Adapters** — Hook: "In a 90-minute round you have models, business rules, storage and a CLI driver. Where does each line go so that a curveball ('add a REST layer', 'swap storage') touches one folder?" · Derive: mixing I/O, rules and storage couples everything → layers with a dependency direction (driver → service → domain ← repository interfaces; adapters implement ports) → the domain has no I/O · Covers: programming to interfaces (declare by the abstraction: `PaymentGateway&`, `List<>`); layered architecture (controller/driver, service/application, domain/model, repository/infrastructure) and the dependency rule; hexagonal / ports & adapters at class level; in-memory repositories as adapters; DTOs vs domain objects at boundaries; package/folder layout for machine coding in C++ (`model/ service/ repository/ strategy/ main.cpp tests.cpp`) and Java (`com.x.model`, …); the anti-pattern of pass-through service layers · Build: `designs/phase-01/layered-skeleton/`: a small "user + orders" app in the layout, with the CLI driver and an in-memory repository; swap in a second repository adapter without touching services; Java package version · Adapt: add a REST-ish command interface next to the CLI; add caching in front of the repository (where does it go?) · Anchors: the machine-coding skeleton (revisited as a kata at 8.1.3), clean architecture diagrams · When-NOT: four layers for a 200-line problem; a "service" that only forwards to the repository · File: `lessons/phase-01/1.2.7-Layering-Ports-Adapters.md` |

## Gate 1

- [ ] For each SOLID principle: states it precisely, gives the violation, the requirement change that exposes it, and the refactor, in ≤ 2 min each, without notes.
- [ ] Given 5 unseen snippets, names the violated principle (or "none, this is fine") with the change that would hurt, ≥ 4/5.
- [ ] Refactors an unseen `switch`-on-type into an OCP-compliant design with tests green throughout, in ≤ 25 min. *(switch: via the OCP lesson build; the kata 1.2.9 is deferred)*
- [ ] Writes a contract test suite that catches an LSP-violating implementation.
- [ ] Inverts a hard-wired dependency with constructor injection, adds a fake, tests a time-dependent rule with a fake clock.
- [ ] Explains DRY-as-knowledge and backs out a wrong abstraction. *(switch: deferred)*
- [ ] Removes a Law-of-Demeter chain by moving behaviour to data; explains when a chain is fine. *(switch: deferred)*
- [ ] Explains the fragile base class problem with the InstrumentedHashSet case and fixes it by composition.
- [ ] In a critique, separates real violations from over-application with a justified call on each.
- [ ] Phase 1 concept map drawn; `reference/principles.md` Phase 1 entries written by the learner.
