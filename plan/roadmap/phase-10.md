# Phase 10 — Case Studies III: Infrastructure-Flavoured Systems

**Why here:** Atlassian, Uber, Microsoft, Adobe and the infra teams at Flipkart/PhonePe like problems
where *the library itself* is the product: a logger, a cache, a rate limiter, a scheduler, a message
queue, a KV store, a file system, an editor, a workflow engine. Here **extensibility** (a new eviction
policy, a new sink, a new algorithm, all without editing the core) and **thread safety** are the whole
point, and the curveballs are exactly "add another policy". Phase 7's components reappear as the
engines inside these systems. Cycle 10.3 adds discussion-style rounds (URL shortener, Stack Overflow,
Cricbuzz) that are often asked without full code.
**Case-study rows:** as in Phase 8. **Scaffolding:** interview conditions throughout.

## Cycle 10.1 — Libraries & frameworks

| ID | Type | Session |
|---|---|---|
| 10.1.1 | MC | **Logger Framework** — Hook: "Design and implement a logging library that application teams will use: log levels, multiple destinations, formatting. It must be thread-safe and must not slow the application down." · Derive: `Logger` (name, level threshold) obtained from a `LoggerRegistry`/`LogManager` with hierarchical names (`app.payments` inherits from `app`), `LogRecord` (level, timestamp, thread, logger, message, context map), **`Appender`/`Sink`** interface (console, file, in-memory for tests) attached per logger (Observer-like fan-out), **`Formatter`** Strategy (plain, JSON), level filtering as a **Chain of Responsibility** or filter list; **async mode**: a bounded queue (7.1.1) + a background writer thread, with a drop/block policy on overflow and flush on shutdown; the hard part: thread-safe appenders (no interleaved lines), the async path's shutdown/flush correctness, and a cheap disabled-level check (no formatting cost) · Covers: levels (TRACE..FATAL), per-logger levels with inheritance, multiple sinks per logger, formatters, contextual fields (request ID: MDC-like thread-local), synchronous and asynchronous modes, flush/close, tests with an in-memory sink, a stress test (16 threads × 10k lines: no torn or lost lines in sync mode; accounted drops in async mode) · Adapt: log rotation by size/time for the file sink (a decorator around the sink?); runtime level change from config without restart; a slow network sink must not block others (per-sink queues); sampling of DEBUG logs at 1% · Anchors: Microsoft/Amazon/Atlassian/Adobe LLD rounds (a classic), log4j/logback/spdlog architecture · When-NOT: a Singleton logger reached from everywhere (inject the `LoggerFactory` or at least keep the singleton an interface); reflection-heavy configuration · File: `designs/phase-10/logger/` |
| 10.1.2 | MC | **Pluggable Cache (LRU/LFU/TTL)** — Hook: "Build an in-memory cache library: get, put, delete, a capacity limit with a pluggable eviction policy, optional TTL per entry. Several services will use it from many threads." · Derive: `Cache<K, V>` facade over a `Storage` (hash map) + **`EvictionPolicy`** interface (`keyAccessed`, `keyAdded`, `keyRemoved`, `evictKey`) with LRU (list + map iterator, O(1)), LFU (frequency buckets + `minFreq`, O(1)) and FIFO implementations; **TTL**: lazy expiry on read + a periodic sweeper or an expiry min-heap; write policies (write-through/write-behind to a loader/`DataSource`: optional); stats (hits, misses, evictions) via an observer/listener; **thread safety**: a global lock first, then sharding (7.2.3); the hard part: keeping the policy's structures consistent with storage on every path (put-existing, delete, expiry, eviction) and O(1) operations · Covers: get/put/delete, capacity with eviction via the chosen policy, TTL with lazy + active expiry (injected clock), cache loader on miss (`getOrLoad`, with single-flight so concurrent misses load once), stats, tests per policy (incl. put of an existing key, capacity 1, TTL boundary), a stress test (no size > capacity, no stale reads after delete) · Adapt: add an eviction policy (e.g. LRU-2 or random) without editing `Cache`; size-based capacity (bytes, not entries); a write-behind policy that batches writes to the backing store; cache-stampede protection under concurrent misses · Anchors: Atlassian/Uber/Microsoft/Flipkart LLD rounds; LeetCode LRU/LFU as the core; Caffeine/Guava design · When-NOT: an Observer framework for stats nobody reads; generic `Cache<K, V>` templates with 6 policy parameters (keep runtime pluggability simple) · File: `designs/phase-10/cache/` |
| 10.1.3 | MC | **Rate Limiter Library** — Hook: "Build a rate limiter library that services can use to limit requests per client and per API. Different APIs need different limits and algorithms. It must be thread-safe." · Derive: `RateLimiter` interface (`tryAcquire(key)` → decision with retry-after), algorithm implementations (token bucket, fixed window, sliding window log, sliding window counter: 7.3.1) behind a **Strategy/factory by config**, a **`RateLimiterRegistry`** mapping (client, API) → limiter created lazily and atomically (`computeIfAbsent`-style, 7.2.3), rules from config (`LimitRule {scope, limit, window, algorithm}`), hierarchical limits (per user AND global: all must allow; no partial consumption), injected clock; the hard part: correct per-key concurrency without a global lock, idle-key eviction, and composite limits consuming atomically · Covers: configure rules, check and consume, per-key isolation, multiple algorithms selectable per rule, retry-after, runtime rule update, idle-key cleanup, fake-clock tests for bursts and window edges per algorithm, a stress test (16 threads never exceed the limit for a key) · Adapt: a new algorithm (leaky bucket queueing) without editing the registry; per-plan limits (free/pro/enterprise) resolved per request; a distributed deployment of 10 instances (explain the options: local limits of N/10, a central store with atomic scripts, a sync'd approximation) · Anchors: Atlassian (a well-known code-design question), Uber, Stripe/Razorpay API throttling · When-NOT: a timer thread per bucket; designing the distributed version in code during a 90-min round (discuss it) · File: `designs/phase-10/rate-limiter/` |
| 10.1.4 | MC | **Task Scheduler / Cron** — Hook: "Build a job scheduler library: schedule one-off jobs at a time or after a delay, recurring jobs by interval or a cron-like expression, cancel jobs, and run them on a worker pool. Show it working." · Derive: `Scheduler` facade; `Job` (id, task, `Schedule`, retry policy, status); **`Schedule`** interface with `nextRun(after)`: `OnceAt`, `FixedRate`, `FixedDelay`, `CronSchedule` (a parser for a cron subset: minute/hour/day-of-month/month/day-of-week with `*`, lists, ranges, steps; Interpreter-lite 4.2.5); a **dispatcher** thread over a min-heap keyed by next-run time with `wait_until` (7.3.2–7.3.3) handing due jobs to a pool (7.1.5); `RetryPolicy` Strategy (none, fixed, exponential with jitter); job listeners (Observer) for status; the hard part: correctness of next-run computation, cancellation races, fixed-rate vs fixed-delay drift, and a clean shutdown · Covers: schedule once/after-delay/fixed-rate/fixed-delay/cron, cancel, list jobs with next run times, retries on failure, concurrency limit per job (no overlapping runs of the same job), status/history, fake-clock tests for cron next-run (month ends, leap years, day-of-week), a threaded test with tolerances · Adapt: priorities among jobs due at the same time; persistence so jobs survive restart (repository + recovery of missed runs: catch-up or skip policy); time-zone-aware cron; a job that must run exactly once across 3 scheduler instances (leader election/locks: discuss) · Anchors: Uber/Atlassian/Microsoft LLD rounds, Quartz/cron/`ScheduledExecutorService` design · When-NOT: full cron syntax (`L`, `W`, `#`) in 90 min: agree on a subset; a thread per job · File: `designs/phase-10/task-scheduler/` |

## Cycle 10.2 — Messaging & storage

| ID | Type | Session |
|---|---|---|
| 10.2.1 | MC | **Pub-Sub / In-Memory Message Queue** — Hook: "Build an in-memory message broker: producers publish to topics, consumers subscribe and receive messages. Multiple consumers, and messages shouldn't be lost if a consumer is slow. Implement it." · Derive: `Broker` with `Topic`s; a topic is an **append-only log** (vector of `Message{offset, key, payload, ts}`) and consumers track **offsets** (Kafka-style) *or* per-subscriber queues (fan-out) with ack/redelivery (RabbitMQ-style): choose and justify; **consumer groups** (each message to one consumer in the group: partition assignment or competing consumers); delivery semantics: at-least-once with acks and redelivery on timeout, a retry count and a **dead-letter queue**; push (dispatcher threads) vs pull (`poll(max)`); per-key ordering via partitions (hash(key) % P); back-pressure and retention; the hard part: concurrency (producers and consumers on many threads), ack/redelivery correctness, and ordering guarantees stated precisely · Covers: create topic (partitions), publish (with key), subscribe (group), poll/consume with ack, redelivery after an ack timeout, DLQ after N failures, replay from an offset, per-partition ordering, a stress test (P producers, C consumers: every message acknowledged exactly once per group in the at-least-once sense, i.e. duplicates allowed but counted, none lost), tests for redelivery and DLQ · Adapt: a new consumer joins a group (rebalance partitions); message TTL/retention by size; filtering subscriptions (by header); exactly-once processing for one consumer via idempotent handlers (dedupe store) · Anchors: Uber/Atlassian/Flipkart/Microsoft LLD rounds; Kafka and RabbitMQ models (the system-design course covers the distributed versions) · When-NOT: disk persistence and replication in 90 min (state them as out of scope); one thread per subscriber per topic · File: `designs/phase-10/pubsub/` |
| 10.2.2 | MC | **Notification Service** — Hook: "Build a notification service used by other teams: send notifications over email, SMS and push using templates, respecting user preferences, with retries. Implement it." · Derive: `NotificationRequest` (user, template id, params, priority, channels or 'by preference'), `TemplateEngine` (placeholder substitution, per channel/locale), `UserPreferences` (opt-outs per category/channel, quiet hours, preferred channel order), **`Channel`/`Sender` interface** per channel with provider adapters (Adapter; Bridge if notification kinds × channels both vary: 3.2.2), a dispatch pipeline (validate → resolve prefs → render → rate-limit per user (10.1.3) → send → record), async sending through a queue + workers (7.1), **`RetryPolicy`** with exponential back-off and failover to a secondary provider, delivery status tracking (Observer/callbacks); the hard part: preferences + quiet hours + retries without a tangle, idempotency (don't send twice on retry of the request), and a new channel as a local change · Covers: send by template with params, channel resolution from preferences, quiet hours (deferred via a scheduler), per-user rate limit, retries with back-off and provider failover, status per notification, bulk send to a segment, fake-clock and fake-sender tests for every rule · Adapt: add WhatsApp (one new sender + template variant); a digest mode batching low-priority notifications hourly; priority notifications (OTP) bypass quiet hours and queues; provider webhooks report delivery failures later · Anchors: Amazon/Flipkart/Swiggy/Atlassian LLD rounds; the system-design course's Notification designs (the distributed half) · When-NOT: a message broker inside the service in a 90-min round (use a local queue; mention the broker); a template language with loops and conditionals · File: `designs/phase-10/notification-service/` |
| 10.2.3 | MC | **In-Memory Key-Value Store with TTL & Transactions** — Hook: "Implement an in-memory key-value store with `SET`, `GET`, `DELETE`, `EXPIRE`/TTL, and transactions: `BEGIN`, `COMMIT`, `ROLLBACK`, which can be nested. Drive it with text commands." · Derive: `Store` (map key → `Entry{value, expiresAt}`), **TTL**: lazy check on access + active expiry (sampling or a heap), injected clock; **transactions as a stack of change layers** (each `BEGIN` pushes a layer recording writes/deletes (tombstones); reads look through layers top-down; `COMMIT` merges the top layer into the one below (or into the store if outermost); `ROLLBACK` pops it) *vs* an undo log of inverse operations (compare); a **command parser + Command objects** (4.1.6) for the driver; `COUNT value`-style secondary queries with an index kept consistent across layers; concurrency: per-client transactions (isolation level stated: e.g. serialise commits with a store lock, or optimistic check of read-set versions at commit); the hard part: nested transaction semantics (tombstones, TTL inside a transaction) and consistency of secondary indexes · Covers: SET/GET/DELETE/EXISTS, EXPIRE/TTL/PERSIST, nested BEGIN/COMMIT/ROLLBACK with correct visibility, `COUNT <value>` in O(1), error messages for bad commands, a scripted driver, tests for nested rollback, delete-then-rollback, TTL expiry inside a transaction, and index consistency · Adapt: snapshot/restore to a file; `WATCH`-style optimistic transactions for concurrent clients; data types beyond strings (lists, counters with `INCR`); eviction when memory is full (reuse 10.1.2) · Anchors: a classic Atlassian/Uber/Stripe-style coding round ("in-memory database with transactions"), Redis semantics · When-NOT: MVCC with garbage collection in 90 min (describe it); a full RESP protocol · File: `designs/phase-10/kv-store/` |
| 10.2.4 | MC | **In-Memory File System** — Hook: "Implement an in-memory file system: `mkdir`, `ls`, `addContentToFile`, `readContentFromFile`, `rm`, `mv`, with paths like `/a/b/c`. Then we'll extend it." · Derive: **Composite** (`Node` → `File`/`Directory`, 3.2.1) with children in an ordered map (sorted `ls`), a `PathResolver` splitting and walking paths (`.`/`..` if asked), `FileSystem` facade; metadata (size, created/modified times via injected clock, owner, permissions); `mv` as detach + attach with cycle prevention (can't move a directory into its own subtree); search via a visitor or predicate walk (`find -name '*.log' -size +1M`: Specification 4.3.2); **permissions** via a protection check (Proxy 3.1.4) or in the facade; concurrency: a `shared_mutex` for the tree or per-directory locks with ordering for `mv`; the hard part: path edge cases, `mv` correctness, and deciding where permissions live · Covers: mkdir -p semantics, ls of file vs directory, create/append/read files, rm (recursive flag), mv/rename, size of a directory (recursive), find by name/size/type, tests for path edge cases (root, trailing slash, non-existent intermediate, file where a directory is expected) · Adapt: symbolic links (a leaf referencing a path; loops); per-user quotas; permissions (rwx for owner/group/other); a watch/notify API on directories (Observer) · Anchors: LeetCode 588 Design In-Memory File System (the core), Amazon/Microsoft/Atlassian LLD rounds (reported) · When-NOT: modelling inodes and blocks; a Visitor for one operation · File: `designs/phase-10/file-system/` |
