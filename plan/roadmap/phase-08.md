# Phase 8 — The Machine-Coding Method + Case Studies I

**Why here:** everything so far (modelling, principles, patterns, tests, concurrency) now has to come
out *under a clock*. A 90-minute round rewards a repeatable method more than brilliance: clarify, model,
skeleton, running core flows by minute 60, tests, then a curveball that measures how local your changes
are. This phase installs the method (8.1), then practises it on games, state machines and the classic
systems that every Indian product company's round draws from.
**Case-study rows:** `Hook` is the prompt as the interviewer states it (short, under-specified on
purpose). `Derive` is the mentor's private map of the expected discovery and is **never shown before
the attempt**. `Adapt` lists the curveballs (one fired at ~minute 60–70, one in review). Every MC ends
with `REVIEW.md` in the design folder and a rubric score (roadmap §9).
**Scaffolding:** MC hints on request, each costs rubric points; Claude calls the time at every phase
boundary. Coached debriefs.
**Language:** each MC in the learner's chosen MC language (decided at intake; C++ by default); at least
two of this phase's MCs in Java if any target company's round is Java-first.

| 8.1.1 | L | **The Machine-Coding Round & the Method** — Hook: "You get a 1-page problem statement for 'Snake & Ladder' and 90 minutes. ## Cycle 8.2 — Games

| ID | Type | Session |
|---|---|---|
| 8.2.1 | MC | **Snake & Ladder** — Hook: "Design and implement Snake & Ladder. Multiple players, the usual rules. You have 90 minutes; I'd like to see it run." · Derive: entities `Game`, `Board` (size, map of jumps), `Jump`/`Snake`/`Ladder` (start → end; a snake is a downward jump: one class with validation or two?), `Player`, `Dice` (interface: `roll()`), `GameStatus`; the turn loop in `Game`, not in `main`; board config validated (no cycles, no snake head on 100, no two jumps from one cell); the hard part: making dice and rules pluggable without over-building · Covers: n players, configurable board size and jumps, one or more dice, exact-landing rule (or not: ask), winner detection and ranking of remaining players, a scripted demo with a seeded random source (injected: 5.2.5) and a deterministic test dice, tests for jumps, chained jumps (ladder to a snake head?), overshoot, winner · Adapt: crooked dice that only roll even numbers (Strategy, one new class); a "roll 6 → roll again, three 6s → lose the turn" rule (where does the rule live?); power-ups on cells; continue until only one player remains · Anchors: Flipkart/Swiggy-style machine coding (very common), LLD practice lists · When-NOT: a Singleton `Game`; an `Observer` for every move; a factory hierarchy for 2 jump types · File: `designs/phase-08/snake-ladder/` |
| 8.2.2 | MC | **Chess (move validation)** — Hook: "Build a two-player chess game engine: the board, the pieces, and legal-move validation. No AI needed. 90 minutes." · Derive: `Board` (8×8 of optional pieces), `Piece` hierarchy with a per-type move generator (virtual `candidateMoves(board, from)`) or movement-rule objects (sliders vs steppers), `Move` (from, to, promotion, flags), `Game` (turn, history, status); the hard parts: blocked sliding moves, **check** (a move is legal only if the own king isn't attacked afterwards: simulate and test), and deciding what to defer (castling, en passant, promotion) explicitly · Covers: all six piece movements incl. captures and blocking, turn alternation, check detection and illegal-move rejection, checkmate/stalemate detection (if time; state the plan otherwise), move history, algebraic input in the driver, tests per piece and for the pinned-piece case · Adapt: add castling (conditions touch history: where's the state?); undo last move (Command/Memento: 4.1.6–4.1.7); a fairy piece (the Archbishop = bishop + knight) without editing other pieces; 3-check variant · Anchors: Amazon/Microsoft OOD discussions (often discussion-only), machine-coding lists · When-NOT: a class per square; Visitor for move generation; a rules engine for chess · File: `designs/phase-08/chess/` |
| 8.2.3 | R | Cycle review: rebuild-back the Snake & Ladder model in 10 min; compare the learner's two MC scores and time logs (where did the minutes go?); the learner starts `reference/case-study-index.md` (system · core abstraction · the hard part · patterns used and why · score · what I'd change) |

## Cycle 8.3 — State machines

| ID | Type | Session |
|---|---|---|
| 8.3.1 | MC | **Vending Machine** — Hook: "Design a vending machine: it holds products in slots, accepts coins and notes, dispenses the product and returns change. Implement it." · Derive: lifecycle-driven behaviour → **State** (Idle, HasMoney, Dispensing, OutOfService) or a transition table; `Inventory` (slot → product + count), `Product` with `Money` price (0.2.5), `CashBox` with denominations; change-making with limited denominations (greedy works for Indian denominations; can fail when coins run out: must detect and refuse *before* taking money), refunds on cancel; the hard part: every event handled in every state without a `switch` explosion, and correct change when the cash box is short · Covers: insert money (multiple coins), select product, insufficient funds, sold out, exact change unavailable (refuse and refund), cancel/refund, dispense and return change, admin restock and cash collection (a mode), tests for every state × event that matters · Adapt: card/UPI payment (a new state with an async "bank approved" event); a maintenance mode that rejects everything; combo offers ("chips + drink ₹10 off"); two users at a double-sided machine (concurrency on the shared inventory) · Anchors: very common in Indian machine-coding rounds and Amazon OOD · When-NOT: State classes for Admin mode if a flag + guard suffices; Observer for a display nobody asked for · File: `designs/phase-08/vending-machine/` |
| 8.3.2 | MC | **ATM** — Hook: "Design an ATM system: card, PIN, withdraw, deposit, balance, mini-statement. Implement the ATM side; the bank can be simulated." · Derive: session **State** (Idle → CardInserted → Authenticated → TransactionInProgress → Idle; lock card after 3 wrong PINs), `BankService` interface (DIP) with an in-memory fake, `CashDispenser` as a **Chain of Responsibility** over denominations (₹2000/500/200/100) or a greedy strategy with availability checks, `Transaction` hierarchy or Command objects, `Account` with `Money`; the hard part: atomicity: never debit without dispensing and never dispense without debiting (debit → dispense → on failure reverse), and daily limits · Covers: PIN verification with retries and card retention, withdrawal with denomination constraints and cassette levels, insufficient funds, daily limit, deposit, balance, mini-statement, cancel at any step, tests for each flow and the dispense-failure reversal · Adapt: the same account used from two ATMs at once (concurrency on balance: lock per account, 7.3.5); cardless UPI withdrawal (new entry path, same states?); dispense fails half-way (partial dispense) · Anchors: classic OOD question (Amazon, Microsoft), Indian machine-coding lists · When-NOT: modelling the bank's core system; a Singleton ATM · File: `designs/phase-08/atm/` |
| 8.3.3 | CR | **Critique: a flawed vending machine**: Claude presents a confident submission (planted flaws, private): state stored as a string and compared in every method; `VendingMachine` exposing `setState()` publicly so the UI changes states; change computed with `double`; money taken before checking change availability; `Inventory` returned by mutable reference to the admin; an unused Singleton; tests only for the happy path. Plus one good decision (the transition-table style). The learner scores it on the rubric as an evaluator would, then lists the three fixes with the highest rubric gain |
| 8.3.4 | R | Cycle review: rebuild-back both state machines' transition tables from memory in 5 min each; update `reference/case-study-index.md`; the learner's own time log across three MCs: is "running by minute 60" happening? |

## Cycle 8.4 — Classic systems

| ID | Type | Session |
|---|---|---|
| 8.4.1 | MC | **Parking Lot** — Hook: "Design a parking lot system. Several floors, different vehicle and spot types, entry and exit gates, tickets and payment. 90 minutes, make it run." · Derive: `ParkingLot` → `Floor`s → `Spot`s (type, occupied-by); `Vehicle` (type, number: value object) vs inheritance-per-vehicle (is behaviour different? usually no → an enum + compatibility rule); `Ticket` (spot, vehicle, entry time), `SpotAllocationStrategy` (nearest to gate / lowest floor / by type), `PricingStrategy` (hourly slabs, per-type rates, flat night rate) with an injected `Clock`; `EntryGate`/`ExitGate` using a `ParkingService`; availability lookup in O(1) per type (free-spot sets per floor/type, not scanning); the hard part: **concurrency**: two entry gates assigning the same last spot (atomic find-and-reserve per spot type) · Covers: park (allocate spot, issue ticket), unpark (compute fee, free spot), availability per floor/type, full-lot handling, lost ticket, display board (Observer, only if time), tests incl. full lot, wrong vehicle for spot type, fee boundaries (exactly 1 h, 1 h 1 min) · Adapt: EV spots with charging billed separately; reservations in advance (a spot is held until a time); multiple entry gates on separate threads (prove no double allocation with a stress test); a vehicle that can use a larger spot when its type is full · Anchors: the single most common LLD question (Amazon, Microsoft, Flipkart, Uber, Walmart, Adobe) · When-NOT: a class per vehicle type with no different behaviour; `ParkingLot` as a Singleton; a DB schema discussion in a machine-coding round · File: `designs/phase-08/parking-lot/` |
| 8.4.2 | MC | **Elevator System** — Hook: "Design an elevator system for a building with N floors and M elevators. Simulate requests and movement. Implement the scheduling." · Derive: `Elevator` (current floor, direction, state: Idle/MovingUp/MovingDown/DoorsOpen/Maintenance, stop set), `Request` (external: floor + direction; internal: destination), `Dispatcher` choosing an elevator via a **`SchedulingStrategy`** (nearest idle, same-direction-on-the-way, LOOK/SCAN), a discrete-time `step()` simulation driven by the driver (testable without threads) vs real threads/actors (7.3.4); the hard part: the per-elevator stop ordering (two sorted sets for up and down legs, LOOK) and a dispatcher that doesn't send three elevators to one call · Covers: external and internal requests, direction-aware servicing, doors open/close at stops, idle elevators parked, capacity (optional), a `step()`-based simulation printing state, tests for LOOK ordering, dispatch choice, and no-starvation of a far request · Adapt: emergency/fire mode (all go to ground, ignore requests: State); a VIP/express elevator serving only floors 20–40 (strategy + constraint); each elevator runs on its own thread (actor model, message passing) and the dispatcher must be thread-safe; a new scheduling algorithm swapped at runtime · Anchors: very common (Amazon, Microsoft, Uber, Atlassian variants) · When-NOT: one thread per elevator in the first version (simulate with `step()` first, then thread if asked); a full physics model · File: `designs/phase-08/elevator/` |
| 8.4.3 | MC | **Library Management System** — Hook: "Design a library management system: members, books, borrowing, returns, fines, reservations. Implement the core." · Derive: `Book` (title, ISBN, authors) vs `BookCopy` (barcode, status) (0.3.3), `Member` with a `MembershipPlan` (limits, loan period), `Loan` (copy, member, due date), `Reservation` queue per *book* (not copy), `FinePolicy` (Strategy, injected clock), `Catalogue` search by title/author (Specification optional), `NotificationService` interface for "reserved copy available" (Observer/event); the hard part: returning a copy that has reservations (hold it for the first reserver with an expiry instead of shelving it) and limits enforced in one place · Covers: add books/copies, search, borrow (limits, availability), return (fine calculation), reserve (queue), hold for reserver with expiry, renew (blocked if reserved), tests for limits, fines at boundaries, reservation handover · Adapt: e-books with a max-concurrent-readers licence; multiple branches with inter-branch transfer; fines waived for premium members (strategy per plan); two members reserving the last copy concurrently · Anchors: classic OOD question; Indian machine-coding lists · When-NOT: a `Librarian` actor class with all the logic; user authentication · File: `designs/phase-08/library/` |
| 8.4.4 | LD | **LLD discussion: Amazon Locker** — Hook: "Design Amazon Locker: customers pick up packages from self-service lockers at locations. Let's talk it through: classes, key flows, trade-offs. You can write a bit of code for the parts you think matter." · Derive: `LockerLocation` → `Locker`s (size S/M/L/XL, state), `Package` (size, order), `LockerAssignmentStrategy` (smallest-fitting, nearest location), `PickupCode` (one-time, expiry), `Reservation`/assignment state machine (Reserved → Delivered → PickedUp / Expired → ReturnToSender), notifications; the hard part: assignment under concurrency (two deliveries racing for the last M locker), code security (hashing, attempts limit), and expiry handling · Covers: requirements and scope (delivery agent flow, customer flow, returns), class diagram with multiplicity, key interfaces with signatures, sequence diagram for delivery and for pickup, the assignment algorithm, concurrency answer, extensibility (temperature-controlled lockers, returns drop-off) · Adapt: the package doesn't fit on arrival; a locker door jams (maintenance state); a location goes offline · Anchors: Amazon SDE-2 LLD rounds (reported), Microsoft OOD · When-NOT: designing the delivery routing system (out of scope: say so) · File: `designs/phase-08/amazon-locker/` |
| 8.4.5 | M | **Mock: 90-min machine coding, Flipkart-style**: an unseen problem from the mock pool (not any case study above; e.g. a coffee machine with recipes and ingredient refills, a car-pooling board, or an in-office cafeteria wallet), stated like a real problem document with must-haves and "bonus" items; interviewer mode throughout; curveball at minute 70; 20-min evaluation discussion; scored /100; `mocks/` file written |
| 8.4.6 | R | Phase review: all Phase 8 scores side by side with per-category averages (which rubric line is weakest?); rebuild-back the parking-lot model + allocation + pricing in 15 min; `reference/case-study-index.md` complete for Phase 8; the learner draws the **Phase 8 concept map** (each case study linked to the patterns and concurrency strategies it used) |

- [ ] Types the MC skeleton from memory in ≤ 10 min, compiling with tests.
- [ ] Runs an LLD discussion round (class diagram, interfaces, sequence diagram, concurrency answer) scoring ≥ 65.
