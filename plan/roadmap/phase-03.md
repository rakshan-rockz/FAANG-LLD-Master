# Phase 3 — Structural Patterns

**Why here:** structural patterns compose objects: wrap them (Adapter, Decorator, Proxy), simplify them
(Facade), build trees of them (Composite), split abstraction from implementation (Bridge), and share
them (Flyweight). They need interfaces (0.1.2) and composition over inheritance (1.2.3). Four of them
share one *shape* (an object holding a reference to another behind an interface), so the key skill is
telling them apart by **intent**, which gets its own compare session.
**Scaffolding:** hints on request only, after an honest attempt.
**Reading (after the sessions):** HFDP ch 3 (Decorator), ch 7 (Adapter & Facade), ch 9 (Iterator &
Composite), ch 11 (Proxy); GoF ch 4 (structural catalogue).

## Cycle 3.1 — Wrapping: Adapter, Facade, Decorator, Proxy

| ID | Type | Session |
|---|---|---|
| 3.1.1 | L | **Adapter** — Hook: "Checkout uses `PaymentGateway::charge(Money, OrderId)`. The business signs with a second provider whose SDK exposes `createTransaction(amountInPaise: long, currency: String, meta: Map)` returning a status string. Integrate it without touching checkout" · Derive: the client's interface is right for the client; the SDK's is fixed → translate between them in one place → an object that implements the target interface and delegates to the adaptee · Covers: object adapter (composition; default) vs class adapter (private inheritance in C++ / not in Java); two-way adapters; adapting units, error models (status codes → exceptions/Result), sync vs async, and identifiers; anti-corruption layer (DDD) as adapter at the domain boundary; adapters in the STL (`std::stack`, `std::queue`, iterator adapters, `std::back_inserter`) and Java (`Arrays.asList`, `InputStreamReader`); testing adapters (contract tests vs the target interface) · Build: `designs/phase-03/payment-adapters/`: two provider SDK stand-ins with deliberately different APIs, two adapters, contract tests run against both; Java version · Adapt: the provider's call becomes async with a webhook; a provider supports refunds partially (LSP check); a third provider in ≤ 10 min · Anchors: payment gateways (Razorpay/PayU/Stripe-style), legacy logging API, XML → JSON service · When-NOT: you own both sides: change one interface instead of adapting; adapters stacked on adapters signal a missing domain interface · 📖 HFDP ch7 · File: `lessons/phase-03/3.1.1-Adapter.md` |
| 3.1.2 | L | **Facade** — Hook: "Placing an order calls inventory (reserve), pricing (quote), payment (authorise), shipping (schedule) and notification (confirm), in the right order with compensation on failure. Four callers (app, web, partner API, admin tool) each re-implement it slightly differently" · Derive: the subsystem is powerful but complicated and every client wires it → a single higher-level entry point that encapsulates the common workflow → clients depend on the facade; power users can still reach the subsystem · Covers: GoF Facade intent (simplify, not hide completely); facade vs service layer vs API gateway (same idea at different scales); keeping the facade thin (orchestration only, no business rules that belong in the subsystem); facades and layering (1.2.7); multiple facades per client type (BFF idea); facade vs Adapter (simplify vs translate) vs Mediator (4.2.2: colleagues know the mediator; subsystems don't know the facade) · Build: `designs/phase-03/checkout-facade/`: a `CheckoutFacade` over 5 fake subsystems with compensation when payment fails; tests for the happy path and each failure step · Adapt: partner API needs a two-step reserve-then-confirm (a second facade method or a second facade?); one subsystem becomes remote and slow · Anchors: checkout, home theatre (HFDP), compiler front-end · When-NOT: a facade over one class (just use the class); a facade that grows every subsystem method becomes a god class · File: `lessons/phase-03/3.1.2-Facade.md` |
| 3.1.3 | L | **Decorator** — Hook: "A `DataSource::read(key)`. Product wants logging on some calls, caching on some, retries on the flaky remote one, and metrics everywhere, in combinations. The subclass version has 12 classes and counting" · Derive: behaviours added by subclassing multiply per combination → wrap an object in another object with the *same interface* that adds one behaviour and delegates → stack wrappers at runtime → combinations are compositions, not classes · Covers: GoF structure (Component, ConcreteComponent, Decorator holding a Component); same interface in and out (the defining constraint); stacking order matters (cache outside retry ≠ retry outside cache) and how to reason about it; C++ ownership (`std::unique_ptr<Component>` chains), decorators with `std::function` wrapping; Java I/O streams (`BufferedInputStream(new FileInputStream…)`) as the canonical example, and its drawback (many tiny classes); decorator vs inheritance vs middleware/pipeline (4.3.4); identity and `instanceof` problems with decorated objects; decorators in Python (`@` syntax, same idea) · Build: `designs/phase-03/datasource-decorators/`: `Logging`, `Caching`, `Retrying`, `Metrics` decorators around a flaky fake source; tests proving each behaviour and one test proving an order-dependent difference; Java version · Adapt: the cache must be bypassed for one call (does the interface need a parameter?); a decorator that needs a method the interface doesn't have (the limit of the pattern) · Anchors: coffee/pizza toppings (HFDP), I/O streams, HTTP client middleware · When-NOT: behaviour that changes the interface (use Adapter); a single fixed combination (just compose it once) · 📖 HFDP ch3 · File: `lessons/phase-03/3.1.3-Decorator.md` |
| 3.1.4 | L | **Proxy** — Hook: "An `ImageGallery` loads 500 full-resolution images at startup and takes 40 s. Also: only admins may call `deleteImage()`, and the image service is on another machine" · Derive: the client must keep using the same interface, but *access* to the real object must be controlled: deferred, guarded, remote, cached → a stand-in with the same interface that controls when/whether/how the real subject is reached · Covers: GoF Proxy; kinds: virtual (lazy creation), protection (authorisation), remote (stub + marshalling), caching, smart reference (refcount, lock-on-access, copy-on-write); C++ smart pointers as proxies; `std::vector<bool>::reference` as a proxy object (and its pitfalls with `auto`); Java dynamic proxies (`java.lang.reflect.Proxy`) and how Spring AOP/`@Transactional` use them (and the self-invocation pitfall); proxy vs decorator (control access vs add behaviour: often identical code, different intent and lifecycle ownership) · Build: `designs/phase-03/image-proxy/`: a virtual proxy that loads on first `display()`, a protection proxy checking roles, tests for each; a Java dynamic-proxy logging example · Adapt: lazy loading must be thread-safe (two threads display at once); the remote call can fail (what does the proxy do?) · Anchors: lazy images, access control, RPC stubs, ORM lazy loading · When-NOT: laziness that moves an unpredictable latency spike into user interactions; protection proxies that duplicate checks the service must do anyway · 📖 HFDP ch11 · File: `lessons/phase-03/3.1.4-Proxy.md` |
| 3.1.5 | C | **Adapter vs Decorator vs Proxy vs Facade** — Hook: "Four snippets, each `class X : public Service { std::unique_ptr<Service> inner; … }` or close to it. Name each pattern — and prove it's not the other three" · Derive: the structure is nearly identical; the difference is **intent** and the interface relation: Adapter changes the interface; Decorator keeps it and adds behaviour; Proxy keeps it and controls access (often owns the subject's lifecycle); Facade offers a new, simpler interface over many objects · Covers: the comparison table (interface in vs out, number of wrapped objects, who creates the wrapped object, typical stacking, client awareness, examples); also Bridge and Composite in the same family picture (preview of 3.2); naming precisely in an interview and why it matters (shared vocabulary, not trivia); 4 "which would you use?" scenarios with curveballs · Build: `designs/phase-03/wrappers-compared/`: the learner classifies and then minimally rewrites 4 given snippets so each correctly expresses its intent · Adapt: a "caching adapter" (two intents in one class: split or keep?) · Anchors: the four snippets, HFDP ch 7 and ch 11 comparisons · When-NOT: arguing names instead of design: if two names fit, describe the intent and move on · File: `lessons/phase-03/3.1.5-Wrappers-Compared.md` |
| 3.1.6 | R | Cycle review: explain-back of the four wrappers by intent; given 5 unseen scenarios, choose the wrapper and sketch it in 2 min each; the learner writes the Phase 3 wrapper entries in `reference/patterns.md` |

## Cycle 3.2 — Trees, bridges and sharing: Composite, Bridge, Flyweight

| ID | Type | Session |
|---|---|---|
| 3.2.1 | L | **Composite** — Hook: "A file explorer shows total size for any node. Files have a size; folders contain files and folders. The first implementation has `if (node.isFolder) … else …` in size, search, delete and permission checks" · Derive: clients distinguish leaves from containers everywhere → give both a common interface so a container's operation is the aggregation of its children's → part-whole hierarchies treated uniformly · Covers: GoF structure (Component, Leaf, Composite with children); recursive operations (size, render, price); **transparency vs safety**: child-management methods (`add/remove`) on Component (uniform but leaves must reject) vs only on Composite (safe but clients must know the type); parent pointers (ownership: children owned by `unique_ptr`, parent as raw observer); ordering, caching aggregated values and invalidation; cycles (a folder inside itself) and how to prevent them; iteration over composites (preview 4.2.3); Visitor as the partner for adding operations (4.2.4) · Build: `designs/phase-03/filesystem-composite/`: `File`/`Directory` with size, find-by-predicate, and delete; tests incl. an attempted cycle; Java version · Adapt: cached sizes that stay correct on changes; symlinks (shortcut nodes: a leaf that references another node); permissions inherited down the tree · Anchors: file systems, org charts, menus, UI widget trees, bundles/combos in a cart · When-NOT: a fixed two-level structure (order → lines) doesn't need a recursive abstraction · 📖 HFDP ch9 · File: `lessons/phase-03/3.2.1-Composite.md` |
| 3.2.2 | L | **Bridge (+ pimpl)** — Hook: "Notifications come in 3 kinds (alert, reminder, promotion) and go over 4 channels (email, SMS, push, WhatsApp). The class list: `AlertEmail`, `AlertSms`, … 12 classes. Add Slack" · Derive: two independent dimensions of variation multiplied into one hierarchy → m × n classes → split into two hierarchies connected by composition (the abstraction holds an implementor) → m + n · Covers: GoF Bridge (Abstraction, RefinedAbstraction, Implementor, ConcreteImplementor); identifying the two axes; bridge vs strategy (structure similar; bridge is about decoupling two hierarchies designed up front); the C++ **pimpl idiom** as a bridge for compilation firewalls and ABI stability (`std::unique_ptr<Impl>`, where to define the destructor, the cost of an extra indirection); drivers (JDBC as a bridge between the API and vendor implementations); shapes × renderers · Build: `designs/phase-03/notification-bridge/`: `Notification` hierarchy × `Channel` hierarchy; add Slack and a new kind, counting files; a pimpl'd class with a stable header · Adapt: a channel that doesn't support rich content (what does the abstraction do?); a kind that must go over two channels · Anchors: notification × channel, shape × renderer, remote × device (GoF), JDBC · When-NOT: only one dimension actually varies; the second "axis" is speculative · File: `lessons/phase-03/3.2.2-Bridge.md` |
| 3.2.3 | L | **Flyweight** — Hook: "A text editor stores a `Character` object per character with font, size, colour and position: a 10-MB document uses 2 GB. A forest renderer has 1 million `Tree` objects each with its own mesh and texture" · Derive: most of each object's state is identical across objects → split intrinsic (shared, immutable) from extrinsic (per-use, passed in or stored separately) state → share one object per distinct intrinsic state via a factory cache · Covers: intrinsic vs extrinsic state; the flyweight factory (`unordered_map<Key, shared_ptr<const Flyweight>>` or interned indices); immutability is mandatory; memory arithmetic (estimate before and after: the learner computes it); string interning, `std::string` SSO vs interning, Java's string pool and `Integer.valueOf` cache (-128..127: the `==` trap); glyphs, game tiles, chess pieces, map markers; flyweight and thread-safety (the factory needs synchronisation; the flyweights don't) · Build: `designs/phase-03/flyweight-forest/`: 1M trees with shared `TreeType`s; measure memory (count bytes by design) before/after; a thread-safe factory · Adapt: a tree can be customised individually (extrinsic override or copy-on-write?); flyweights must be garbage-collected when unused (weak references) · Anchors: text glyphs, forests/particles, chess pieces, map tiles · When-NOT: few objects or little shared state: the factory and extrinsic plumbing cost more than they save · File: `lessons/phase-03/3.2.3-Flyweight.md` |
