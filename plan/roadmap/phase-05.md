# Phase 5 — Clean Code, Testing & Refactoring

**Why here:** the rubric gives *testing* 10 points and *code quality* 5, and evaluators read your code
for 20–30 minutes after a machine-coding round. More importantly, refactoring is how patterns are
*reached* in real code, and tests are what make refactoring safe. The learner writes their own tiny
test framework (5.2.2) and uses it in every later build. Testable design (injecting time, randomness
and I/O) is the prerequisite for testing concurrent code in Phases 6–7.
**Scaffolding:** hints on request only, after an honest attempt.
**Reading (after the sessions):** *Clean Code* (Martin) ch 2 (names), 3 (functions), 7 (error
handling), 9 (unit tests), 10 (classes), 17 (smells and heuristics); *Refactoring* 2nd ed. (Fowler)
ch 1 (the first example), 2 (principles), 3 (bad smells), 4 (building tests). Optional: *Working
Effectively with Legacy Code* (Feathers) ch 1–4 and 25 for 5.1.5.

| 5.1.2 | L | **Error Handling: exceptions vs error codes vs `optional` vs `Result`** — Hook: "`bookSeat()` can fail because the seat is taken, the show has started, the payment was declined, or the DB is down. Four callers handle it four ways; one ignores a return code and sells the seat twice" · Derive: some failures are *expected domain outcomes* (the caller must decide), some are *programmer errors* (bugs), some are *environmental* (retry or propagate) → choose the mechanism by the category: return values/`Result` for expected outcomes, exceptions for exceptional/environmental conditions, assertions for bugs · Covers: error codes (ignorable; `[[nodiscard]]`), exceptions (non-local, can't be ignored, cost model: zero-cost happy path, expensive throw; exception safety guarantees revisited from 0.2.1; `noexcept`), `std::optional` (absence without a reason), a hand-written **`Result<T, E>`** (C++23 `std::expected` isn't in GCC 11: the learner writes a minimal one with `std::variant`), domain error types (enums or exception hierarchies); Java checked vs unchecked exceptions and the debate, `Optional` (return type only), custom exception hierarchies; don't return null; don't use exceptions for control flow; translating errors at layer boundaries (adapter 3.1.1); logging vs throwing (not both); error handling in machine-coding drivers (clear messages, no crash) · Build: `designs/phase-05/booking-errors/`: `bookSeat()` returning `Result<Booking, BookingError>` for domain failures and throwing only for infrastructure failures; tests for each path; Java version with a sealed result or exceptions · Adapt: a batch booking of 5 seats where 1 fails (partial success type); retries for transient failures only · Anchors: booking/payment failures, parsing, file I/O · When-NOT: `Result` types threaded through ten layers for errors nobody handles in between (let exceptions propagate there) · 📖 CC ch7 · File: `lessons/phase-05/5.1.2-Error-Handling.md` |

| 5.1.4 | L | **Refactoring Moves (small steps, always green)** — Hook: "Fowler's video-store / theatre-invoice statement function: add HTML output and new play types. Do it without ever having red tests for more than a minute" · Derive: big-bang rewrites break things and lose behaviour → tiny behaviour-preserving transformations, each followed by running the tests → the design emerges step by step · Covers: the definition (behaviour-preserving, in small steps); the core moves with mechanics: extract/inline function, extract/inline variable, change function declaration, encapsulate variable/collection, introduce parameter object, combine functions into class, split phase, extract class, move function/field, replace temp with query, **replace conditional with polymorphism**, replace type code with subclasses/State/Strategy, replace primitive with object, replace inheritance with delegation, remove flag argument, decompose conditional, guard clauses; IDE automated refactorings vs manual; refactoring vs changing behaviour (two hats); when to refactor (rule of three, preparatory, comprehension, litter-pickup); refactoring toward a pattern (Kerievsky) · Build: `designs/phase-05/theatre-statement/`: Fowler's ch 1 example in C++ (or Java): characterisation tests, then the full refactoring sequence with the tests run after every step; the learner logs each move · Adapt: add a new play type and HTML output after the refactor (count the edits) · Anchors: Refactoring ch 1 example, Gilded Rose (5.1.6) · When-NOT: refactoring code you're about to delete; refactoring without tests (you're just editing) · 📖 Refactoring ch1 · 📖 Refactoring ch2 · 📖 CC ch10 · File: `lessons/phase-05/5.1.4-Refactoring-Moves.md` |
| 5.1.5 | DD | **Legacy Code: characterisation tests & seams** — Hook: "A 2,000-line class with no tests, a hard-coded database call and a static clock. | 5.2.1 | L | **Unit Testing Fundamentals** — Hook: "Your Parking Lot demo prints the right output for the 3 cases you tried. The evaluator runs a 4th: a full lot, a vehicle leaving twice, a ticket for another lot. How would *you* have found those first?" · Derive: a demo is not a test; tests are executable specifications that run in seconds → Arrange-Act-Assert, one behaviour per test, names that state the behaviour → choose cases by boundaries and equivalence classes, not by what you remember · Covers: what a unit is (a behaviour, not a class or a method); AAA/Given-When-Then; FIRST (fast, independent, repeatable, self-validating, timely); test naming (`rejects_exit_for_unknown_ticket`); boundary value analysis and equivalence partitioning; testing state vs interactions; one assert concept per test; the test pyramid (unit / integration / end-to-end) and where machine-coding tests sit; fixtures and helpers without hiding the logic; tests as documentation for the evaluator; what to test in a 90-min round (core flows + the 3 nastiest edge cases; the learner's checklist); **test doubles and fake clocks in brief** (full treatment 5.2.4); Java JUnit 5 overview (and why the course uses plain `assert` + `java -ea` without a build tool) · Build: `designs/phase-05/testing-basics/`: a test suite for a provided `Wallet` class using plain `assert` with one `main`, then noting what's painful (no names, stops at first failure, no summary): the motivation for 5.2.2 · Adapt: a test that depends on the current time; a test that depends on hash-map iteration order (both flaky: why?) · Anchors: wallet, parking lot, stack · When-NOT: testing private helpers directly; tests that mirror the implementation line by line · 📖 CC ch9 · 📖 Refactoring ch4 · File: `lessons/phase-05/5.2.1-Unit-Testing-Fundamentals.md` |
| 5.2.2 | K | **Kata: write your own test framework (`minitest.hpp`)**: target 30 min. | 5.2.3 | L | **Test-Driven Development** — Hook: "Build a bowling score calculator (strikes, spares, 10th frame) by writing one failing test at a time. | 5.2.4 | L | **Test Doubles: dummies, stubs, spies, mocks, fakes** — Hook: "Test that an order confirmation SMS is sent exactly once, that the 'quiet hours' rule delays it, and that a gateway timeout triggers one retry, without a real SMS provider or waiting until 23:00" · Derive: the collaborator is slow, non-deterministic or has side effects → replace it with a controllable stand-in through the seam created by DI (1.2.6) → choose the simplest double that verifies the behaviour · Covers: Meszaros' taxonomy (dummy, stub, spy, mock, fake) with a C++ example of each (hand-written, via interfaces); **fake clock** and fake random source for deterministic time/randomness; in-memory fakes of repositories and gateways (and keeping fakes honest with contract tests, 1.1.4); state verification vs behaviour verification; over-mocking (tests coupled to implementation, brittle refactors); "don't mock what you don't own" (wrap it in an adapter, mock the adapter); Java: Mockito basics (`when/thenReturn`, `verify`) and hand-written fakes; gMock mention for C++ · Build: `designs/phase-05/notification-doubles/`: the SMS scenario tested with a spy sender, a fake clock and a stub gateway that times out once; the same test done with an over-specified mock to see it break on a harmless refactor · Adapt: the retry uses exponential backoff with jitter (fake random); the SMS sender is called from another thread (preview 6.x) · Anchors: notification, payment gateway, rate limiter with a clock · When-NOT: mocking value objects or pure functions; mocking every collaborator of a class · File: `lessons/phase-05/5.2.4-Test-Doubles.md` |
| 5.2.5 | L | **Testable Design** — Hook: "`LateFeeCalculator` reads `time(nullptr)`, calls `Database::instance()`, and prints to `std::cout`. ## Gate 5

- [ ] Names ≥ 15 smells with their refactorings; finds the top 5 in an unseen 150-line file in ≤ 10 min. *(switch: deferred to the depth pass; smells are called out in critiques and MC reviews)*
- [ ] Refactors an unseen function with tests green after every step (≤ 5 min red at any point). *(switch: deferred)*
- [ ] Chooses exception / `Result` / `optional` / assertion correctly for 6 unseen failure scenarios and implements a minimal `Result<T, E>`.
- [ ] `designs/lib/minitest.hpp` written by the learner and working (registration, CHECK/REQUIRE/CHECK_EQ/CHECK_THROWS, summary, exit code).
- [ ] Tests a time-dependent rule deterministically with a fake clock and a collaborator with a spy/fake.
- [ ] Refactors hidden time/global/I-O dependencies into a testable core. *(switch: explained at 5.2.1 scope; the full build is deferred)*
- [ ] TDDs a small kata with visible red-green-refactor steps. *(switch: deferred)*
- [ ] In a critique, identifies ≥ 5 of 7 test flaws and rewrites the worst two. *(switch: deferred)*
- [ ] Phase 5 concept map drawn.
