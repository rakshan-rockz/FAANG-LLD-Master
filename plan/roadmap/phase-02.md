# Phase 2 — Creational Patterns (+ Object Pool, DI Container)

**Why here:** after DIP, the next question is *who creates the concrete objects?* `new ConcreteX`
scattered through business code is the first place coupling hides and the first place a curveball
("add a new vehicle type", "a second payment provider") hurts. Creational patterns move creation to one
place. Singleton is taught with its thread-safe implementations *and* why it's usually an anti-pattern.
**Scaffolding:** hints on request at any rung; Claude offers H0 after ~5 min of silence.
**Reading (after the sessions):** *Head First Design Patterns* (2nd ed., HFDP) ch 4 (Factory), ch 5
(Singleton); *Design Patterns* (GoF) ch 1 (introduction) and ch 3 (creational catalogue).

| 2.1.5 | L | **Builder** — Hook: "`Order(customerId, items, address, coupon, giftWrap, note, deliverySlot, paymentMode, isExpress)`. | 2.1.6 | L | **Prototype** — Hook: "A game level editor lets designers configure a 'goblin' (stats, equipment, AI settings) and then stamp out 500 of them, each slightly modified. ## Cycle 2.2 — Singleton, object pool, DI container

| ID | Type | Session |
|---|---|---|
| 2.2.1 | L | **Singleton (and its thread-safe implementations)** — Hook: "Config is loaded from disk in four places at startup, each with a different copy; a logger opened twice interleaves lines. 'Make sure there's exactly one.' Then: two threads call `getInstance()` at the same moment" · Derive: exactly one instance + a global access point → a private constructor + a static accessor → lazy init races under threads → thread-safe initialisation · Covers: GoF Singleton intent (one instance *and* global access, two separate concerns); C++: **Meyers singleton** (function-local static, thread-safe since C++11 "magic statics"), `std::call_once`, eager static init; double-checked locking and why the naive version is broken (reordering; needs atomics with acquire/release, revisited 7.2.5); Java: eager `static final`, synchronized accessor, DCL with `volatile`, the **holder idiom** (Bill Pugh), **enum singleton** (serialisation/reflection safe); deleting copy/move; destruction order at exit · Build: `designs/phase-02/singleton/`: Meyers singleton + a `call_once` version; a stress program with 16 threads calling the accessor, asserting one construction (`tools/stress.sh`); Java holder + enum versions · Adapt: the config must be reloadable at runtime; tests need a different config per test (→ 2.2.2) · Anchors: config, logger, metrics registry, ID generator · When-NOT: whenever "exactly one" is just "we only happen to create one": create one in `main` and inject it (2.2.2) · 📖 HFDP ch5 · File: `lessons/phase-02/2.2.1-Singleton.md` |
| 2.2.2 | DD | **Singleton as an Anti-Pattern, and the Alternatives** — Hook: "Tests pass alone and fail when run together. Two tests both mutate `Config::instance()`; a third depends on a `Logger` singleton that was destroyed before a static object's destructor logged" · Derive: a singleton is global mutable state with hidden dependencies → order-dependent tests, invisible coupling, lifetime fiascos → separate 'one instance' (a composition-root decision) from 'global access' (the harmful part) → inject the single instance · Covers: hidden dependencies (signatures lie); testability (can't substitute; resetting hacks); static initialisation order fiasco and destruction order (C++); multiple singletons in plugins/shared libraries; concurrency bottleneck (a global lock); alternatives: DI of a single instance, context/environment objects, monostate (and its problems), "singleton per scope" (per request/tenant); when a singleton is acceptable (stateless or append-only infrastructure: logger, metrics registry) and how to make it test-friendly (an injectable interface with a default instance); how to answer "would you use a singleton here?" in an interview · Build: `designs/phase-02/singleton-refactor/`: reproduce order-dependent test failures, then refactor to injection with a composition root; both suites run · Adapt: per-tenant config (singleton breaks, DI scales); a legacy codebase where you can't change 200 call sites (a seam: `Config::instance()` delegating to an injectable provider) · Anchors: config/logging/DB-connection singletons, "Singletons are pathological liars" (Hevery) · When-NOT: the anti-pattern label doesn't mean "never": a stateless logger facade is fine · File: `lessons/phase-02/2.2.2-Singleton-Anti-Pattern.md` |
| 2.2.3 | L | **Object Pool** — Hook: "Each request opens a new DB connection (50 ms). At 200 requests/s the database refuses connections; memory spikes from buffers allocated per request" · Derive: expensive, reusable resources created per use → keep a bounded set, lend them out, get them back → the return must be guaranteed (RAII) and the pool must be thread-safe and bounded · Covers: acquire/release protocol; RAII handles returning to the pool (`unique_ptr` with a custom deleter, or a handle class); bounded size, blocking vs failing when exhausted, timeouts; validation on borrow/return (a broken connection); reset state on return (leaking one user's data to the next); sizing; thread-safety (a mutex + condition variable: preview of 7.1.1); real pools (HikariCP, thread pools, `std::pmr` memory pools, game object pools); leaks and leak detection · Build: `designs/phase-02/object-pool/`: a generic `Pool<T>` handing out RAII handles, max size, `tryAcquire` with timeout, reset-on-return; tests incl. exhaustion and handle-destroyed-early; Java version with `try-with-resources` · Adapt: evict idle objects after N seconds; a borrower crashes holding an object (with RAII it can't leak; in Java?) · Anchors: connection pool, buffer pool, thread pool (7.1.3) · When-NOT: cheap objects (pooling small objects often loses to the allocator and adds bugs); pooling for "performance" without a measurement · File: `lessons/phase-02/2.2.3-Object-Pool.md` |
| 2.2.4 | DD | **Build a Tiny DI Container** — Hook: "Your composition root in `main` has 40 lines of `auto x = make_unique<X>(*y, *z)`. How do Spring and Guice do this, and could you write one in 60 lines?" · Derive: wiring is a graph of constructors → register a factory per type, resolve recursively → lifetimes (singleton vs transient) → cycle detection · Covers: registration (`bind<Interface, Impl>()`), resolution by type (C++ `std::type_index` + type-erased factories with `std::any`/`std::function`; Java `Class<?>` keys), lifetimes (singleton, transient, scoped), constructor injection automation and its limits in C++ (no reflection: factories registered explicitly), cycle detection during resolution, error messages; how Spring works (component scanning, reflection, proxies, `@Scope`), Guice modules; container as a service locator if used from business code (the anti-pattern again); why machine-coding rounds should use manual DI · Build: `designs/phase-02/di-container/`: a C++ container with `registerSingleton/registerTransient/resolve`, cycle detection, tests; a Java version using `Supplier` maps · Adapt: named bindings (two `PaymentGateway`s); scoped lifetime per request · Anchors: Spring/Guice internals, mini-IoC exercises · When-NOT: any codebase where manual wiring fits on one screen · File: `lessons/phase-02/2.2.4-DI-Container.md` |
| 2.2.5 | K | **Kata: registry factory + builder**: target 25 min. Checks: builder product immutable, invalid builds rejected, warnings clean · File: `designs/kata/pizza-builder/` |
