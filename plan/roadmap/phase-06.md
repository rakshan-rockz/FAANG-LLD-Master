# Phase 6 — Concurrency I: Writing Correct Concurrent Code

**Why here:** Uber, Microsoft, Walmart, Adobe, Salesforce and the Indian payments companies ask
concurrency directly (multithreaded printing puzzles, "make this class thread-safe", "implement a
blocking queue"), and *every* booking/money/inventory case study is graded on concurrency safety.
This phase builds the primitives from the hazard up: a race is observed before a mutex is named; a
busy-wait burns a core before a condition variable is named; a deadlock is produced on purpose before
lock ordering is named. Needs RAII (0.2.1), testable design (5.2.5) and minitest (5.2.2).
**Tools:** `tools/stress.sh` (hundreds of runs, timeouts to catch hangs, some runs on one core).
ThreadSanitizer is used automatically where it links; on this machine it doesn't, so evidence comes
from repetition, invariant assertions, injected `sleep`/`yield` at suspicious points, and reasoning
about interleavings, which is the skill interviews test anyway.
**Scaffolding:** max H2 before the time box ends; H3+ only after. No fix is accepted without the
interleaving that broke the old code.
**Reading (after the sessions):** *C++ Concurrency in Action* 2nd ed. (Williams, CCiA) ch 2, 3, 4, 5;
*Java Concurrency in Practice* (Goetz et al., JCIP) ch 2, 3, 5, 10, 16.

| 6.2.2 | DD | **The C++ Memory Model (and the Java Memory Model)** — Hook: "Thread A: `data = 42; ready.store(true, relaxed);` Thread B: `while (!ready.load(relaxed)); assert(data == 42);`. ## Cycle 6.3 — Liveness, coordination primitives and the classic puzzles

| ID | Type | Session |

| 6.3.1 | L | **Deadlock** — Hook: "`transfer(a, b)` locks `a` then `b`. Two users transfer to each other at the same moment. The app freezes. Now reproduce it on purpose, then make it impossible, not just unlikely" · Derive: each thread holds one lock and waits for the other's → a cycle in the wait-for graph → break one of the four Coffman conditions; the practical ones: a global lock order, acquiring all at once, or back-off · Covers: Coffman conditions (mutual exclusion, hold-and-wait, no pre-emption, circular wait); **lock ordering** (by account ID; by address as a last resort; hierarchical lock levels with runtime checks); `std::scoped_lock`/`std::lock` (deadlock-avoidance algorithm); `try_lock` with back-off (and its livelock risk); lock timeouts; deadlocks with one lock (self-deadlock without recursion, waiting on a future under a lock), with condition variables, and through callbacks (calling out while holding a lock: "open calls" in JCIP); detection: wait-for graphs, Java thread dumps (`jstack`) and `ThreadMXBean.findDeadlockedThreads`, `gdb thread apply all bt`; resource-ordering in LLD systems (seats, wallets, inventory items) · Build: `designs/phase-06/deadlock/`: reproduce the transfer deadlock reliably (`tools/stress.sh` reports hangs), fix it by ID ordering and by `scoped_lock`, and write a hierarchical mutex that aborts on an order violation; Java version with `tryLock` + timeout · Adapt: transfer among *three* accounts (split payment); an account's lock is also taken by an interest job iterating all accounts · Anchors: bank transfer, dining philosophers (6.3.4), nested monitor lockout · When-NOT: `try_lock` loops as a first resort (use ordering); a single global lock to "avoid deadlock" (throughput dies) · 📖 JCIP ch10 · File: `lessons/phase-06/6.3.1-Deadlock.md` |
| 6.3.2 | L | **Livelock, Starvation, Fairness & Priority Inversion** — Hook: "The deadlock fix used `try_lock` + retry. Now two threads politely back off forever.
