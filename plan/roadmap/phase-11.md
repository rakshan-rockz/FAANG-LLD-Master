# Phase 11 — Interview Mastery

**Why last:** by now the learner can design and build. This phase converts ability into *offers*:
the exact formats of each target company, the evaluation discussion after a build (defending code
under questioning), extensibility curveballs at speed, whiteboard LLD rounds with no compiler, and
the sealed baseline redo that measures the whole course. Human mocks are strongly recommended
alongside (≥ 4, with peers or a mock platform); their feedback enters `progress/weak-areas.md`.
**Scaffolding:** cold, company-styled, strict scoring, hints cost points everywhere.

## Cycle 11.2 — Curveballs & defence

| ID | Type | Session |
|---|---|---|
| 11.2.1 | DD | **Extensibility Curveball Gym** — Hook: "Take four of your own case-study codebases. I'll fire 12 requirement changes, 3 per system, at 90-second intervals. For each: which files change, what new class appears, what gets retested, and is any existing test now wrong?" · Derive: extensibility is measured, not claimed → predict the change set before editing → where predictions miss, the design hid a dependency · Covers: curveball taxonomy (new variant of an existing axis, a new axis, a cross-cutting concern such as audit/rate limit/multi-tenancy, a scale/concurrency change, a rule that crosses aggregates); answering in the interview format ("I'd add a `XStrategy`; `Service` doesn't change; one new test class; the config registry gets one line"); implementing 2 of the 12 live to check the predictions; recording prediction accuracy · Build: `designs/phase-11/curveball-gym/`: the prediction log + 2 implemented curveballs per system in the learner's existing designs · Adapt: a curveball that *should* change the core (recognise it and say why) · Anchors: the learner's own Phase 8–10 designs · When-NOT: pre-building extension points for every possible curveball (that's the over-engineering trap in reverse) · File: `lessons/phase-11/11.2.1-Curveball-Gym.md` |
| 11.2.2 | DD | **Code-Walkthrough Defence** — Hook: "The evaluator opens your 800-line submission and says: 'Walk me through it. Why is this a class? Why not an interface here? What happens if two requests hit this at once? Where are your tests for this path?' You have 20 minutes" · Derive: evaluators test whether you *own* your design → a structured tour and crisp, honest justifications (including "I'd change this") score higher than defensiveness or over-claiming · Covers: the 2-minute tour (entities → core flow → extension points → concurrency → tests → known gaps); answering "why" questions with the force behind the choice; admitting a weakness and stating the fix; handling a challenge you disagree with (evidence, not stubbornness); questions evaluators ask repeatedly (by category, from Phases 8–10 reviews); walking through a flow with a sequence diagram on the fly; pointing at the test that proves a claim · Build: none: 3 recorded walkthroughs of the learner's own MCs under hostile questioning, graded · Adapt: the evaluator finds a real bug live (the recovery script) · Anchors: Flipkart/PhonePe evaluation discussions, Atlassian follow-ups · When-NOT: memorised justifications that don't match the code · File: `lessons/phase-11/11.2.2-Code-Walkthrough-Defence.md` |
| 11.2.3 | LD | **LLD Discussion Gym: 3 × 20-minute rounds**: three unseen prompts in rapid succession (e.g. a jukebox/music player, a deck-of-cards game framework, an online auction; or learner-weak domains from the index), each to a class diagram + key interfaces + one sequence diagram + one concurrency answer in 20 min; scored on the LD rubric per round; the learner compares first-5-minute questions across rounds |
| 11.2.4 | CR | **Critique from the evaluator's seat**: Claude presents a complete, anonymised 90-min candidate submission for an unseen problem (mixed quality: a solid core, a god class, a race, missing tests, one over-engineered corner, one elegant extension point); the learner evaluates it *as an interviewer*: scores it on the rubric with justifications, writes the feedback form, and lists the three questions they'd ask in the discussion. Compared against the mentor's scoring (target: within ±8) |
| 11.2.5 | R | Cycle review: curveball prediction accuracy, walkthrough grades, LD gym scores; weak areas re-tested; playbook final edit |

## Gate 11 (final)

- [ ] Baseline redo scores ≥ 80 and improves on the baseline in every rubric category (or the regression is explained).
- [ ] Three company-format mocks in a row ≥ 80 (Hire band): machine coding, code design, LLD discussion.
- [ ] A concurrency-core mock ≥ 75 with a stress-tested invariant and a correct interleaving argument.
- [ ] Curveball predictions ≥ 80% accurate on own designs. *(switch: deferred)*
- [ ] A code-walkthrough defence graded "owns the design" by the mentor.
- [ ] Evaluator-seat critique within ±8 of the mentor's score. *(switch: deferred)*
- [ ] All four `reference/` files complete and accurate; course concept map drawn. *(switch: patterns + concurrency-primitives + case-study-index for the switch rows)*
- **Switch track only (Gate 10 folded in):** the cache, rate limiter and pub-sub builds each have a passing stress test and fake-clock tests, and each extension curveball was a one-file change.
