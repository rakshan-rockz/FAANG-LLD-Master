# Phase 7 — Concurrency II: Concurrent Structures & Concurrency in Systems

**Why here:** Phase 6 made single classes correct. This phase builds the *components* interviews ask
for by name (bounded blocking queue, thread pool, readers–writers lock, concurrent LRU, token-bucket
rate limiter, delayed-task scheduler) and then turns to the design question every booking, payment
and inventory round contains: *two users do the same thing at the same moment: what happens?*
Needs all of Phase 6.
**Scaffolding:** max H2 before the time box ends; H3+ only after. Every lab ends with the invariant
argued in writing.
**Reading (after the sessions):** CCiA ch 6 (lock-based concurrent data structures), ch 7 (lock-free),
ch 9 (advanced thread management, pools); JCIP ch 6 (task execution). Optional: JCIP ch 8 (applying
thread pools), *The Art of Multiprocessor Programming* ch 10–11 for 7.2.2.

| 7.2.1 | L | **Readers–Writers** — Hook: "A product catalogue is read 50,000 times/s and updated 5 times/s. With one mutex, readers queue behind each other for no reason; after switching to a shared lock, updates sometimes wait 30 s" · Derive: reads don't conflict with each other → allow concurrent readers, exclusive writers → reader preference starves writers; writer preference starves readers → policy choice, or avoid locking reads altogether (copy-on-write / RCU-style snapshots) · Covers: `std::shared_mutex` + `std::shared_lock`/`std::unique_lock`; reader vs writer preference and starvation (6.3.2); **implementing a RW lock from mutex + cv** (with a writer-waiting flag for writer preference); upgrade/downgrade (why lock upgrades deadlock with two upgraders); when a shared lock is slower than a mutex (short critical sections, cache-line ping-pong on the reader count); copy-on-write snapshots with `std::shared_ptr<const T>` + atomic swap (`std::atomic<std::shared_ptr>` in C++20; GCC 11 lacks it: `std::atomic_load/store` free functions), RCU idea; Java `ReentrantReadWriteLock` (fairness, no upgrade), `StampedLock` (optimistic reads, validation), `CopyOnWriteArrayList` · Build: `designs/phase-07/rwlock/`: a writer-preferring RW lock from mutex + cv, a catalogue using it, a copy-on-write catalogue; stress (readers never see a half-applied update; writers wait bounded); benchmark both vs a plain mutex · Adapt: a reader needs to upgrade to update a missing entry; 1 update/s but each rebuild costs 200 ms (COW cost) · Anchors: config caches, routing tables, catalogues, DNS caches · When-NOT: write-heavy or tiny critical sections (a plain mutex wins) · File: `lessons/phase-07/7.2.1-Readers-Writers.md` |
| 7.2.2 | DD | **Lock-Free Basics: CAS, the Treiber Stack, ABA, Reclamation** — Hook: "A lock-free stack: `push` is a CAS loop on `head`. `pop` reads `head`, reads `head->next`, CASes `head` to `next`. Under stress it occasionally returns a node that was already popped and freed" · Derive: CAS only checks that the pointer value is the same, not that the node wasn't removed and reused in between (ABA) → tag the pointer with a version counter, or never reuse memory while any thread might read it (hazard pointers / epochs) → memory reclamation is the hard part of lock-free code · Covers: lock-free vs wait-free vs obstruction-free progress; the Treiber stack (push/pop CAS loops, memory orders); **ABA** (the interleaving, why it's real with free lists and allocators); fixes: tagged/versioned pointers (double-width CAS, `std::atomic<struct{ptr, tag}>` and `is_lock_free`), hazard pointers, epoch-based reclamation, deferred reclamation, and the C++26 direction (`hazard_pointer`, RCU); why Java's GC removes most of the reclamation problem (`AtomicReference`, `ConcurrentLinkedQueue` / Michael–Scott queue), `AtomicStampedReference` for ABA; performance reality (lock-free is not automatically faster; contention on one CAS location) and when it's worth it (latency-critical, no blocking in signal handlers/real-time) · Build: `designs/phase-07/treiber-stack/`: a lock-free stack that leaks nodes (no reclamation: correct but leaky), then an ABA-prone reuse version with an explanation of the failing interleaving, then a tagged-pointer version; stress + comparison with a mutex stack · Adapt: make pop return by value safely; a bounded lock-free SPSC queue (6.2.3) vs MPMC (why much harder) · Anchors: Treiber stack, Michael–Scott queue, `ConcurrentLinkedQueue` · When-NOT: any LLD interview answer where a mutex meets the requirement; say "lock-free only with a measured need" · 📖 CCiA ch7 · File: `lessons/phase-07/7.2.2-Lock-Free-Basics-ABA.md` |
| 7.2.3 | DD | **Concurrent Hash Map & Concurrent LRU** — Hook: "The LRU cache from your DSA work gets one global mutex. At 16 threads, throughput is flat: every `get` takes the lock *and* writes (moves the node to the front)" · Derive: one lock serialises everything, and LRU's `get` is a write → partition the key space (lock striping / sharding) so unrelated keys don't contend → per-shard LRU approximates global LRU → or record accesses in buffers and apply them in batches (Caffeine-style) → read-mostly paths avoid exclusive locks · Covers: global lock baseline; lock striping (N mutexes by `hash(key) % N`), per-bucket locks; resizing under concurrency (why it's hard: stop-the-world vs incremental); Java 7 `ConcurrentHashMap` segments → Java 8 CAS on empty bins + `synchronized` on bin heads + tree bins, `compute`/`merge` atomic operations, weakly consistent iterators, why `size()` is approximate; concurrent LRU designs: sharded LRU (per-shard capacity and its skew), `shared_mutex` for lookups + deferred promotion, CLOCK/second-chance approximation (reads only set a bit), access buffers + a maintenance lock (Caffeine / W-TinyLFU mention); readers–writers use (7.2.1) and its limits here; invariants to test (size ≤ capacity, no lost entries, map ↔ list consistency) · Build: `designs/phase-07/concurrent-map/`: a striped hash map with atomic `computeIfAbsent`; design notes for three concurrent LRU variants (implemented in 7.2.4) · Adapt: a hot key hammered by all threads (sharding doesn't help: why?); per-entry TTL · Anchors: `ConcurrentHashMap`, Caffeine, Guava cache, memcached · When-NOT: striping for a cache used by 2 threads; a clever design with no invariant tests · 📖 CCiA ch6 · File: `lessons/phase-07/7.2.3-Concurrent-HashMap-LRU.md` |
| 7.2.4 | CL | **Thread-safe LRU lab**: Build: (a) LRU with a global mutex (`std::list` + `unordered_map<key, iterator>`); (b) a sharded LRU (N shards, each (a)); (c) optional: CLOCK approximation with atomic reference bits.
